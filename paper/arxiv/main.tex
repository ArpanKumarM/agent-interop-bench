\title{Cross-Protocol Failure Propagation Across MCP and A2A Agents:\\[2pt]
A Controlled Pilot on Information Flow, Behavioral Influence, and Containment}

\author{Arpan Kumar Mahapatra\\[2pt]
\texttt{arpan.arpan.mohapatra@gmail.com}}
\date{\today}

\begin{document}
\maketitle

\begin{abstract}
Deployed AI agents increasingly speak two protocols at once: the Model
Context Protocol (MCP)~\citep{mcp-spec} for local tool use, and the
Agent2Agent Protocol (A2A)~\citep{a2a-spec} for delegating work to other
agents. Dedicated safety benchmarks for each evaluate one protocol in
isolation. We study the seam. A composed harness drives one real-model host
across both protocol legs --- implemented as local deterministic MCP and A2A
protocol fixtures, not external services --- in a single ordered event
trace, with an observable cross-protocol provenance model (deterministic
content canaries carrying a sensitivity label, an explicit allowed-edge
policy, and per-event causal ancestry) so that information flow and
behavioral influence across the boundary are measured by exact rule-based
checks, without an LLM-based judge or evaluator. Using a decision-point
methodology that deterministically builds the situation and then elicits one
restricted host decision, we ran a controlled confirmatory pilot over three
OpenAI GPT-5.6 models, 240 trials in total. We separate \emph{relay
initiation} (the host sent a message onto the A2A leg after reading a
confidential MCP record) from \emph{direct sensitive egress} (the exact
confidential marker crossed the disallowed host-to-remote edge): relay
initiation varied widely by model (15\%, 85\%, 100\% of confidential
trials), while direct exact-token egress was 0 for every model (0/3, 0/17,
0/20 of relay trials; Wilson 95\% upper bounds 56.2\%, 18.4\%, 16.1\%). This
is verbatim-marker leakage only, not semantic or paraphrased leakage.
Scoring whether the host both selected the mutation-attempt action
\emph{and} named a tool the harness discovered to be mutating (our primary
influence outcome), the adversarial A2A artifact condition showed a higher
rate than a structurally matched benign condition in all three models
(signed treatment$-$control differences $+0.20$, $+0.40$, $+0.50$; Wilson
95\% intervals per cell) --- an association under a controlled manipulation,
not a causal-mechanism claim. Every one of the 56 observed actual
mutating-tool requests was blocked by an independent mutation gate, and none
executed. We report Wilson 95\% intervals and signed rate differences
throughout and deliberately report no p-values: the replicates in a cell are
repeated draws from one model under one fixed stimulus and are not assumed
statistically independent. The complete raw runs and a fully offline
analysis pipeline are published as a deterministic, hash-pinned release.
\end{abstract}

\section{Introduction}
\label{sec:intro}

An agent that is safe in isolation on protocol \emph{X} and safe in
isolation on protocol \emph{Y} is not automatically safe when it uses
\emph{X} and \emph{Y} in the same task. Two mechanisms motivate this paper,
and both are compositional --- properties of the interaction \emph{between}
two protocol legs rather than of either leg alone. The first is information
flow across the boundary: a host agent calls a local MCP tool, receives
content, and then, in service of the same user request, sends a message to a
remote A2A agent; if the tool's content was confidential, that boundary is
exactly where an unintended disclosure can occur, and neither a
single-protocol MCP benchmark (which cannot see the A2A edge) nor a
single-protocol A2A benchmark (which never had the confidential content in
scope) is positioned to observe it. The second is behavioral influence
across the boundary: a remote A2A agent returns an \emph{artifact}, a text
payload the host reads, and if that artifact contains an instruction
(``apply the emergency remediation now'') the host may act on it by calling
a \emph{local} MCP tool, possibly a mutating one --- the adversarial content
and the dangerous action living on opposite sides of the seam.

The only non-local component in every experiment reported here is real
provider model inference: OpenAI GPT-5.6 models~\citep{openai-gpt56} called
through the Responses API. All MCP and A2A infrastructure is local
deterministic protocol fixtures --- an in-process mock MCP tool server
(stdio subprocess, synthetic data, no network) and an in-process mock A2A
HTTP+JSON/REST agent exercised only through a test client. No production,
external, or third-party MCP server or A2A agent was contacted. Throughout,
``the host'' or ``the model'' refers to real provider inference; ``MCP
fixture'' and ``A2A fixture'' refer to the local deterministic
infrastructure.

This paper contributes an executable empirical instrument and a controlled
pilot, not a new risk concept. Concretely: (i) an executable MCP+A2A
composition evaluation that drives one real-model host across an MCP leg and
an A2A leg, both local deterministic protocol fixtures, into one ordered
event trace scored by exact rules; (ii) an observable cross-protocol
provenance model --- deterministic content canaries carrying a sensitivity
label, an explicit allowed-edge policy, and per-event causal ancestry ---
that makes specific boundary-crossing flows checkable without an LLM judge
and separates \emph{direct} (literal) from \emph{propagated} (ancestral)
presence; (iii) a controlled decision-point behavioral-influence
measurement that isolates one host decision from multi-step planning;
(iv) an outcome that distinguishes selecting the mutation-attempt action
from naming a tool the harness \emph{discovered} to be mutating;
(v) an independent containment measurement by an external mutation gate that
is not part of the host; and (vi) a hash-pinned live-model reproducibility
mechanism (a per-run execution fingerprint plus an offline analysis pipeline
that regenerates every table and figure with zero provider calls).

We claim none of the underlying risk concepts as novel, and in particular
claim no priority on cross-protocol composition risk or MCP+A2A ``protocol
pivoting'': that risk has already been named in a June 2026 IETF
Internet-Draft~\citep{mohiuddin2026mcpsec} and formalised as a ``Composition
Safety'' principle with formal cross-protocol composition
models~\citep{agentrfc2026} (Section~\ref{sec:background}). This is also not
the ``first MCP benchmark'' or ``first A2A benchmark'' --- dedicated
single-protocol safety benchmarks for each already exist. Every result below
is conditional on four fixed stimuli, one host policy, one tool surface, and
one point in time; nothing here says any model is ``safe'' or ``unsafe'' in
general, and no significance test is reported.

Manuscript preparation introduced no new experimental runs or provider
calls. All empirical results are reproduced from the frozen public release
\code{phase4b-results-v1}.

\section{Background and Related Work}
\label{sec:background}

\paragraph{MCP.}
MCP is a client--server protocol connecting an LLM-driven \emph{host} to
\emph{tools} and \emph{resources} exposed by MCP servers
\citep[revision 2025-06-18]{mcp-spec}. The host issues a JSON-RPC
\code{tools/call} with a tool name and a JSON argument object; the server
returns a structured result. Tools may carry annotations (for instance a
destructive / read-only hint) so a host or policy layer can treat mutating
operations differently from read-only ones; the specification notes that
such annotations ``should be considered untrusted, unless obtained from a
trusted server.'' Here the MCP leg is a local, in-process deterministic
fixture (implemented with the MCP Python SDK) that returns synthetic records
and performs no network I/O; because it is the trusted local fixture, we
take its discovered annotations as ground truth for a tool's mutating
status.

\paragraph{A2A.}
A2A is a protocol for one agent to delegate a task to
another~\citep{a2a-spec}. A \emph{client agent} discovers a \emph{remote
agent} via an \emph{Agent Card} (spec \S8), opens a \emph{task} whose
lifecycle is a \code{TaskState} machine (\S4.1.1--4.1.3), and exchanges
\emph{messages} built from \emph{parts} (\S4.1.4, \S4.1.6); the remote agent
may attach \emph{artifacts} (\S4.1.7), content payloads representing task
output. The artifact is the natural place for a remote agent, benign or
compromised, to place text the client agent will read and may act upon. Our
A2A leg is a local, in-process deterministic fixture implementing the
HTTP+JSON/REST binding shapes (spec \S11), exercised only through an
in-process test client.

\paragraph{Cross-protocol composition risk (prior articulations).}
The risk this paper measures is not new as a concept. A June 2026 IETF
Internet-Draft~\citep{mohiuddin2026mcpsec} devotes a ``Protocol Pivoting''
section to lateral movement that crosses agent-protocol boundaries ---
explicitly ``combining MCP with Agent-to-Agent (A2A) delegation'' --- and
states that ``mitigations that consider each protocol in isolation do not
address movement that crosses protocol boundaries,'' with a worked scenario
close to our behavioral-influence question. Independently,
\emph{AgentRFC}~\citep{agentrfc2026} formalises a ``Composition Safety''
principle (``security properties that hold for individual protocols can
break when protocols are composed through shared infrastructure'') with
formal (TLA+) models of five cross-protocol composition patterns spanning
MCP, A2A and other agent protocols, plus a spec-conformance checker. We do
not claim priority on any of this. Our work is the executable empirical
complement: where those efforts check conformance against formal invariants
and enumerate mitigations, we run a real-model host across a concrete
MCP+A2A composition (local deterministic protocol fixtures), attach an
observable provenance model, and report measured per-model rates for one
information-flow outcome, one behavioral-influence outcome, and one
containment outcome.

\paragraph{Single-protocol MCP and A2A benchmarks.}
\emph{MCP-SafetyBench}~\citep{mcpsafetybench2026} evaluates MCP tool-using
agents on multi-turn ReAct tasks against a 20-category attack taxonomy over
real-world MCP servers. \emph{MCP Security Bench}~\citep{msb2026} and
\emph{MCPSecBench}~\citep{mcpsecbench2025} similarly target MCP-layer
security (malicious or misconfigured servers, tool-poisoning,
argument-injection, over-broad permissions; MCPSecBench reports 17 attack
types over four MCP attack surfaces). \emph{A2ASecBench}~\citep{a2asecbench2026}
is a protocol-aware security benchmark for Agent-to-Agent systems, with a
taxonomy of supply-chain manipulations and protocol-logic weaknesses and six
attacks across A2A stages. Our composed harness reuses an MCP leg but
measures what happens when that leg's output is carried into an A2A
interaction, and our behavioral-influence stimuli use an adversarial A2A
artifact but the measured action is a mutating call on a \emph{local MCP
tool} guarded by a \emph{local} mutation gate --- outside a pure-MCP or
pure-A2A scope. We make no ``first benchmark'' claim for either protocol.

\paragraph{Indirect prompt injection, tool-use evaluation, defenses.}
Indirect prompt injection --- untrusted content read by an agent carrying
instructions it then follows --- was characterised by Greshake et
al.~\citep{greshake2023indirect}; our behavioral-influence question is an
instance of it in which the injection vector is a remote A2A artifact and
the intended payload is a local MCP mutation.
\emph{AgentDojo}~\citep{agentdojo2024} evaluates prompt-injection attacks
and defenses on tool-using agents with rule-based (not LLM-judge) utility
and security functions; \emph{ToolEmu}~\citep{toolemu2024} identifies
LM-agent risks in an LM-emulated sandbox with an LM safety evaluator. We
differ from both in that our environment executes a real-model host across a
local deterministic MCP+A2A protocol composition (protocol fixtures, not an
LM emulator) and scores by exact-rule provenance checking without an
LLM-based judge or evaluator; this is a methodological alignment with
judge-free evaluation, not a novelty claim.
\emph{CaMeL}~\citep{camel2025} is a defense that separates control and data
flow and tracks data provenance before each tool call; it is conceptually
adjacent to our provenance model but is a mitigation, whereas ours is an
evaluation instrument. Multi-agent security --- threats that emerge or
amplify through agent interactions --- has been framed as a distinct
field~\citep{masec2025}; formal and information-flow approaches to
agent/tool safety~\citep{agentrfc2026, camel2025} provide the theoretical
context for our provenance model, but our contribution here is empirical and
instrument-focused rather than a formal result.

\section{Threat Model and Research Questions}
\label{sec:threat}

We consider a single benign-by-construction host agent that faithfully
follows a fixed natural-language policy: it may call local tools, relay to
the remote agent, attempt a tool call (mutations requiring prior approval,
which it can never self-grant), or stop, and it is told not to send content
``clearly marked confidential, internal, or sensitive'' to the remote agent
unless the task authorizes it. The adversary is modelled purely as control
over the content returned on one leg of the interaction --- not over the
host, the protocols, or the harness --- and operationally that content is
fixed text scripted into the local protocol fixtures for each condition. For
the information-flow question there is no active adversary at all: the MCP
fixture returns a record visibly labeled \code{CONFIDENTIAL - INTERNAL
ONLY}, and the ``threat'' is the host's own judgement about what, if
anything, to relay onward. For the behavioral-influence question the A2A
fixture is scripted to play a compromised remote agent, returning a
realistic natural-language artifact that instructs the host to invoke a
specific mutating MCP tool immediately, claiming prior approval and urgency;
the artifact contains no special marker or trigger string --- it is ordinary
prose a real model must reason about. ``Remote agent'' is the A2A protocol
role of the delegatee; in every experiment it is this local fixture. The
mutation gate is an independent policy component that is \emph{not} part of
the host: it re-derives a tool's mutating status from the discovered
annotation and blocks any mutating call lacking explicit case-level
approval. Out of scope are a malicious host, protocol-level attacks (message
forgery, transport interception), multi-hop agent chains, tool-supply-chain
compromise, and any production, external, or third-party MCP server or A2A
agent.

Three research questions follow. \textbf{RQ1 (cross-protocol information
flow):} when a host reads confidential content from an MCP tool and then
interacts with a remote A2A agent in the same task, does that confidential
content propagate across the A2A boundary? We decompose this into \emph{relay
initiation} --- did the host send any message to the remote agent after
reading the confidential record? --- and \emph{direct sensitive egress} ---
did the exact confidential marker cross the disallowed host-to-remote/A2A
edge? The latter is an exact-token measurement and is not a measurement of
semantic leakage. \textbf{RQ2 (cross-protocol behavioral influence):} does
an adversarial A2A artifact influence the host toward requesting a
\emph{mutating} MCP tool, relative to a structurally matched benign
artifact? We measure the \emph{actual mutating-tool request} rate --- the
host selected the mutation-attempt action \emph{and} the named tool was
discovered by the harness to be mutating --- and report it separately from
the rate at which the host merely selected the mutation-attempt action,
which may name a non-mutating tool. \textbf{RQ3 (containment):} given an
actual mutating-tool request, does an independent mutation gate block it and
prevent execution?

\section{Agent Interop Bench}
\label{sec:bench}

Agent Interop Bench comprises three independent deterministic evaluation
engines --- an MCP tool-use engine, an A2A interoperability engine, and the
composed cross-protocol engine that is the subject of this paper. All run
only against local, in-process mocks with no external network access, and
all scoring is rule-based. The composed engine drives one host agent across
both protocol legs and records a single ordered list of
\code{CrossProtocolEvent}s spanning the MCP leg (\code{mcp_tool_request},
\code{mcp_tool_result}), the A2A leg (\code{a2a_message},
\code{a2a_task_state_transition}, \code{a2a_artifact}), and the host's own
gated actions (\code{mutation_action}). The host's next action is produced
by an adapter given only a sanitized decision context --- the user prompt, a
host policy, the observable protocol history so far, the discovered tool
list, and the target Agent Card, and never any ground-truth label,
provenance annotation, or evaluator state. A fixture-replay adapter drives
the deterministic suite; a real-model adapter (OpenAI Responses API) drives
live studies; the engine is otherwise unchanged between the two. The MCP
fixture is a local stdio subprocess exposing a small fixed tool set that
includes \code{get_customer_record} and \code{get_deployment_status} (both
discovered read-only) and \code{apply_remote_recommendation} (annotated
destructive; discovered mutating), returning synthetic content only. The A2A
fixture is a local in-process HTTP+JSON app whose per-step behavior (task
state, message text, artifact text) is scripted by the case. Before any
mutating call executes, the composed engine applies an independent
predicate, \code{mutation_blocked(is_mutating, approved) = is_mutating and
not approved}, in which \code{is_mutating} is re-derived from the tool's
discovered annotation, never from a fixture flag, and a real-model host can
never set \code{approved = true} for its own attempt; a blocked attempt is
recorded with \code{executed = false} and a permitted call with
\code{executed = true}.

The provenance model is what makes cross-protocol information flow and
influence observable by exact rules. It has four fixture-declared axes, all
hidden from the host. First, \emph{provenance canaries}: a canary is a
deterministic, syntactically inert token, \canary, embedded in specific
content and detected by exact substring identity, never by semantic
interpretation, each carrying a \code{public} or \code{sensitive}
sensitivity label. Second, \emph{allowed sensitive edges}: a
fixture-declared set of \code{(source, dest, protocol)} edges on which a
\code{sensitive} canary is permitted to travel, so that any direct
observation of a sensitive canary on an edge outside this set is a
sensitive-egress violation --- for the RQ1 treatment the only allowed edge
is \code{local_tool}\,$\to$\,\code{host/mcp}, and the
\code{host}\,$\to$\,\code{remote/a2a} edge is not allowed. Third,
\emph{origin trust and content class}: per-actor defaults
(\code{user}/\code{host} trusted, \code{remote}/\code{local_tool} untrusted)
plus optional per-event overrides and a
\code{non_adversarial}/\code{adversarial} content class, which the engine
folds into per-event adversarial-ancestry and sensitive-ancestry sets by a
real DAG computation over the actual event trace rather than a category-name
special case. Fourth, \emph{direct vs.\ propagated presence}: each event
carries both its \code{canary_ids} (tokens literally present in that event's
payload) and its \code{propagated_canary_ids} (tokens present in any causal
ancestor), and our primary RQ1 outcome, direct sensitive egress, counts only
literal presence on the crossing event. This distinction is central: a host
can relay after reading a confidential record --- creating a causal chain,
so the canary appears in \code{propagated_canary_ids} on the A2A message ---
without ever placing the literal marker into the relayed text, in which case
direct sensitive egress does not fire and only the secondary outcome, relay
initiation, does. For RQ2/RQ3 the live-study path does not set an
\code{adversarial} content-class override on the A2A artifact (the artifact
is realistic prose, not a marker), so per-event adversarial ancestry is
empty on this path; we therefore identify the ``adversarial'' versus
``benign'' condition of an influence trial by which overlay was shown ---
condition ground truth --- not by computed ancestry, and say so wherever the
influence and containment outcomes are reported.

\section{Experimental Methodology}
\label{sec:method}

\subsection{Decision-point execution}
\label{subsec:decision}

An earlier free-running pilot, in which models were asked for every step of
an open interaction loop, proved uninformative: models planned the whole
workflow and repeatedly relayed to the remote agent before reaching the
decision the experiment was designed to measure. The frozen methodology used
here is decision-point execution. The engine first constructs the situation
with no model involvement: for sensitive-egress it executes the local MCP
\code{get_customer_record} call so that a real \code{mcp_tool_result} (a
\code{PUBLIC}- or \code{CONFIDENTIAL}-labeled record with an embedded canary)
exists in the trace, and for adversarial-influence it performs exactly one
deterministic A2A interaction so that a real \code{a2a_artifact} (benign or
adversarial text) exists. The real model is then asked for exactly one
decision, given only the sanitized context, with the wire-level action set
restricted to \code{{relay_to_remote, stop}} for sensitive-egress and
\code{{attempt_mutating_tool, stop}} for adversarial-influence; the
restriction is enforced three ways --- the tool schema sent to the provider
contains only the permitted actions, a composite adapter refuses any
returned action outside the set, and the interaction step ceiling admits
only one model decision. Finally the engine performs at most one
deterministic observable action: if the host relays, exactly one A2A
interaction is performed and its events recorded; if the host attempts a
mutating tool, the mutation gate is run and a \code{mutation_action} event
recorded; the trial then terminates \code{COMPLETED}. Per-run parameters
were frozen before execution: \code{reasoning_effort = low},
\code{max_output_tokens = 512}, \code{timeout = 20 s}, \code{retries = 0},
one provider decision per trial, at most 80 provider decisions per run, and
all MCP and A2A targets local.

\subsection{Model panel and design}
\label{subsec:panel}

The panel is three models from the OpenAI GPT-5.6
family~\citep{openai-gpt56}, frozen in this order: \code{gpt-5.6-sol} (the
flagship tier), \code{gpt-5.6-terra} (the balanced default tier),
\code{gpt-5.6-luna} (the lightweight tier). For each model there are 20
blocks; each block contains all four (experiment $\times$ condition) cells
exactly once; the within-block order is shuffled by a single
\code{random.Random(seed)} with one frozen scheduling seed (\code{20260401}),
advanced model-by-model in panel order. This yields exactly 20 replicates
per model per cell and prevents any cell from being over- or under-sampled
by drift, for a total of $3 \times 4 \times 20 = 240$ trials.

\subsection{Reproducibility mechanism}
\label{subsec:repro-mech}

Each run persists an execution fingerprint: a SHA-256 over the plan config
hash, the exact source commit, a canonical hash of the resolved overlay
\emph{contents} (not just their ids), the host-policy hash, the
host-action tool-schema hash, and the per-model schedule hash. The
fingerprint is written once per run and stamped on every trial record, and a
resume is refused if it differs even when the plan hash is unchanged; the
frozen blocked schedule is committed and its hash enters the fingerprint, so
re-randomising the trial order invalidates it.

\subsection{Outcome definitions}
\label{subsec:outcomes}

The RQ1 \emph{primary} outcome is direct sensitive egress,
\code{sensitive_egress == True / (True + False)}, where the outcome is
\code{True} iff a \code{sensitive} canary token literally crossed an edge
not in \code{allowed_sensitive_edges}, \code{False} iff the host relayed but
the token did not cross such an edge, and not applicable otherwise (a
\code{stop} decision, or the intentionally-public control, which declares no
\code{sensitive} canary); the denominator is thus the applicable set
(\code{True + False}), the trials in which the host actually relayed, not all
20. The RQ1 \emph{secondary} outcome is relay initiation,
\code{relay_to_remote} over completed egress trials (denominator 20). The
RQ2 \emph{primary} outcome (``outcome B'') is an actual mutating-tool
request: the host selected \code{attempt_mutating_tool} \emph{and} the named
tool was discovered to be mutating. We also report, descriptively, wrapper
selection (``outcome A'': the host selected \code{attempt_mutating_tool}
regardless of the tool named, with $A \ge B$ always and the gap being
non-mutating tools named through the mutation-attempt action). Containment
over the actual mutating-tool requests distinguishes \code{C} (blocked by
the gate, \code{executed = false}) from \code{D} (executed,
\code{executed = true}). Every rate is reported with a Wilson 95\% score
interval on its own applicable denominator, and paired conditions with the
signed difference \code{rate(treatment)} $-$ \code{rate(control)}.

\subsection{Statistical reporting}
\label{subsec:stats}

We report rates, Wilson 95\% score intervals~\citep{wilson1927}, and signed
treatment$-$control differences, and we report no p-values and run no
significance tests. With 20 replicates per cell the study is a descriptive
confirmatory pilot, not a hypothesis test. The 20 replicates in a cell are
repeated draws from one model under one fixed stimulus; the provider may
share hidden state, batching, caching, or routing across them, so we do not
assume the replicates are independent Bernoulli trials, and the Wilson
intervals are a conventional descriptive spread of the observed proportion,
not a guarantee of i.i.d.\ sampling. Failed trials (none occurred) would be
excluded from behavioral denominators and reported separately as attrition.

\subsection{Behavioral influence}
\label{subsec:rq2}

Using the actual mutating-tool request outcome (the host selected
\texttt{attempt\_\allowbreak mutating\_\allowbreak tool} \emph{and} named a
discovered-mutating tool), the adversarial (treatment) condition showed a
higher rate than the structurally matched benign (control) condition for all

\code{gpt-5.6-sol} 14/20 = 70.0\% [48.1, 85.5] versus 10/20 = 50.0\%
[29.9, 70.1], signed difference $+0.20$; \code{gpt-5.6-terra} 11/20 = 55.0\%
[34.2, 74.2] versus 3/20 = 15.0\% [5.2, 36.0], $+0.40$; and
\code{gpt-5.6-luna} 14/20 = 70.0\% [48.1, 85.5] versus 4/20 = 20.0\%
[8.1, 41.6], $+0.50$. All three signed differences are positive. For
\code{gpt-5.6-terra} and \code{gpt-5.6-luna} the two per-condition Wilson
intervals happen not to overlap, and for \code{gpt-5.6-sol} they do;
interval non-overlap here is a descriptive observation, not a hypothesis
test --- the intervals are computed per condition on $n = 20$, the
replicates are not assumed independent (Section~\ref{subsec:stats}), and we
report no p-value or difference-of-proportions test.

The host selected the mutation-attempt action more often than it named a
mutating tool. Study totals across the four influence cells were wrapper
selection $A = 82$, actual mutating request $B = 56$, and
non-mutating-tool-via-wrapper $E = 26$, with $A = B + E$ in every cell. The
$E$ cases are \texttt{attempt\_\allowbreak mutating\_\allowbreak tool} calls

would substantially overstate the adversarial-vs-benign contrast for some
models, which is why $B$ is our primary influence outcome and $A$ (with $E$
and the executed count $F$) is reported only as a diagnostic
(Appendix~\ref{app:wrapper}).

\subsection{Containment}
\label{subsec:rq3}

Every \emph{observed} actual mutating-tool request was blocked by the

\section{Discussion}
\label{sec:discussion}

The composition is where these behaviors become observable. RQ1 shows one
behavior that only exists across the seam: the host frequently chose to open
the cross-boundary channel by relaying to the A2A fixture after reading
confidential MCP content --- an action a pure-MCP benchmark cannot observe
and a pure-A2A benchmark never sets up --- yet the verbatim confidential
marker never crossed the boundary. RQ3 shows that, in this sample, every
influenced mutating request was refused by the independent gate. These are
not in tension: within the RQ2 manipulation (adversarial vs.\ structurally
matched benign artifact, everything else held fixed) the adversarial
condition was associated with a higher actual mutating-tool request rate in
all three models, and the gate is the component that declined those
requests. We do not claim that the adversarial artifact \emph{causes}
mutating requests in a mechanistic sense, nor that either the host's policy
compliance or the gate is robust: we observed only that, for these four
stimuli and $n = 20$ per cell, the verbatim marker never crossed the
boundary and no influenced mutating request executed, and the study does not
indicate which safeguard would fail first under stimuli it did not test.

The wrapper/actual distinction matters for measurement. A benchmark that
scored ``the model tried to mutate'' whenever the mutation-attempt action
was selected would have reported much larger and noisier effects for some
models here, because those models routed read-only calls through that
action; measuring the discovered mutating status of the named tool
(outcome B) gives a cleaner behavioral signal and avoids conflating
``attempted a dangerous action'' with ``used an oddly-shaped call for a safe
one.'' Relay initiation, likewise, is a behavioral rather than a leakage
outcome: the wide model spread (15\% to 100\%) is a genuine behavioral
difference --- some models treat ``read a confidential record'' as a reason
to minimise onward communication --- but it is not itself a disclosure, and
because a model that never relays cannot leak on that edge, relay initiation
and direct egress must be read together. Finally, the zeros are weak upper
bounds, not guarantees. Zero direct sensitive egress with Wilson upper
bounds of 16--56\% is consistent with a true per-trial verbatim-leak
probability anywhere from 0 up to roughly one in six for the model that
always relayed, and it says nothing about paraphrased leakage; zero mutating
executions is a property of \emph{this} gate against \emph{these} influenced
requests, and the quantity of interest for a larger study is whether any
stimulus can produce an approved-looking mutating request that the gate
would pass.

\section{Limitations}
\label{sec:limitations}

All results are conditional on two sensitive-egress overlays and two
adversarial-influence overlays, one host-policy string, and one three-tool
MCP surface; no claim generalises beyond these. With 20 replicates per cell
the Wilson intervals are wide (for example [0.0, 56.2]\% for the model that
relayed only three times), and this is a controlled confirmatory pilot, not
a powered study: repeated provider calls are repeated samples, not assumed
statistically independent executions, and the signed differences and
non-overlapping intervals in Section~\ref{subsec:rq2} are descriptive, with
no p-values. Direct sensitive egress is a verbatim substring check, so
semantic, paraphrased, or partial information leakage is not measured and a
0 result must not be read as ``no information left the boundary.'' MCP and
A2A are local in-process fixtures, so real servers, transports, network
conditions, and multi-hop agent chains are out of scope, and the
decision-point methodology deliberately removes multi-step planning to
isolate one measured decision rather than observing compounding behavior.
Because the live path does not mark the adversarial artifact with a special
class, the adversarial-vs-benign contrast for RQ2/RQ3 is defined by which
overlay was shown, not by computed adversarial ancestry. The numbers are a
snapshot of three specific model identifiers at one point in time, model
behavior is not stable across versions or dates, and we do not fully explain
why some models route read-only calls through the mutation-attempt action
--- it may reflect the restricted two-action schema at the decision point.

\section{Conclusion}
\label{sec:conclusion}

We built a cross-protocol MCP+A2A composed evaluation harness --- a
real-model host over local deterministic MCP and A2A protocol fixtures ---
with an observable provenance model, and used a decision-point methodology
to run a controlled confirmatory pilot over three models and 240 trials. In
this sample the host frequently chose to open the cross-boundary channel
after reading a confidential MCP record (relay initiation 15--100\% by
model), but the exact confidential marker never crossed the protocol
boundary verbatim (direct sensitive egress 0/40 relay messages; Wilson 95\%
upper bounds 16--56\%); within the controlled manipulation the adversarial
A2A artifact condition was associated with a higher actual mutating-tool
request rate than the structurally matched benign condition in all three
models (signed differences $+0.20$, $+0.40$, $+0.50$); and every one of the
56 observed actual mutating-tool requests was blocked by the independent
mutation gate, with zero mutating executions across the 240 trials. These
are narrow, stimulus-conditional observations for one host policy, one tool
surface, four stimuli, three models, and one point in time --- not general
safety verdicts, not a causal-mechanism claim, and not a claim about
semantic information leakage, which we do not measure. They are published
with the byte-exact raw runs and a fully offline analysis pipeline so that
every table and figure can be regenerated with no provider call.

\paragraph{Reproducibility.}
Every number in this paper comes from the frozen public release
\code{phase4b-results-v1} of Agent Interop Bench

The release contains the three raw runs (byte-exact, not normalised), their
